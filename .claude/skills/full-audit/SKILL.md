# 全体監査ワークフロー

過去に約2〜3週間おきの頻度で(リリース判断前、区切りの依頼時、特定フェーズ着手時)
複数観点での監査を繰り返し実施してきた。定期スケジュールはなく、ユーザー主導で
都度発火する。1回の監査規模は「特定サイトの深掘り」〜「11観点+補足5観点の網羅監査」
までさまざま。依頼の粒度に応じて観点数を選ぶ。

## 観点カタログ

依頼内容に応じて以下から必要な観点を選ぶ(全部を毎回やる必要はない)。

| 観点 | 具体的に見るもの |
|---|---|
| コード品質/正確性 | normalizer誤変換、adapterのsilent drop(抽出済みフィールドを構築子に渡し忘れ)、テーブル列ズレ |
| セキュリティ | PII漏洩(電話番号伏字の表記バリエーション漏れ)、SQLi(LIKEワイルドカード未エスケープ)、レート制限 |
| プライバシー/公開データ境界 | 死亡個体の公開API列挙、第三者(発見者等)個人情報の混入 |
| 技術CI/デプロイ | 環境変数(localhost罠)、Vercel/Cloud Run/Supabase設定、lint/mypy/E2Eゲートの実効性 |
| SEO/集客 | sitemap取得速度、OGP画像、robots.txt、Search Console実インデックス状況、構造化データ |
| 収集品質/網羅性 | フィールド欠損率、silent failure(next/image remotePatterns漏れ等)、消滅個体の扱い |
| 法務 | スクレイピング適法性(L1-L5)、画像著作権(軽微利用)、利用規約棚卸し |
| マネタイズ/戦略 | コスト構造、手離れ度、bus factor |
| 監視/運用 | Discord通知の実効性、シークレット失効の早期検知、自己修復(auto-fix)の健全性 |

## 過去に繰り返し見つかっている問題パターン(重点チェック)

毎回の監査で再発しやすいので優先的に確認する:
- **PII伏字漏れの再発**: 電話番号等の表記バリエーション(括弧/ドット/スペース/国際表記)を追加するたびに新たな漏れが出る
- **adapterのフィールド脱落**: 抽出はできているのに正規化層への配線を忘れる。1サイトで見つかると同型adapterに横展開している可能性が高い
- **環境変数/デプロイ設定の未反映**: コードは健全でも外部インフラ設定が律速していないか
- **シークレットのローテーション漏れ**: APIキー失効に気づかず数週間放置していないか
- **「サイレントに劣化」して気づかれない障害**: fallbackが「成功」として見える、画像取得の静かな失敗、sitemapタイムアウト等

## 実施フロー

1. 依頼のスコープを確認する(全観点の網羅監査か、特定テーマの深掘りか)。曖昧なら
   ユーザーに聞く前に、直近のメモリ(project_*.md)から「前回どこまで見たか」を
   確認し、未着手/再発しやすい観点を優先候補として提示する
2. 規模が大きい(4観点以上)場合は、ユーザーが明示的にオプトインしていれば
   Workflowツールで観点ごとに並列agentを立てて調査→findingsを集約する。
   オプトインが無ければ通常のAgent(Explore/general-purpose)を並列起動する
3. 見つかった問題は深刻度でトリアージする(CRITICAL/HIGH/MEDIUM/LOW)。
   「過去に繰り返し見つかっている問題パターン」に該当するものは優先度を上げる
4. Codexなど別ツールでの独立レビューがあれば、指摘の中でfalse positiveの
   可能性があるものは実装を読んで検証してから採否を決める(鵜呑みにしない)
5. 確定した問題は個別PRとして修正する(1PR=1論理的変更の原則を崩さない)
6. 監査結果と判定(Go/Conditional Go/No-Go等)をメモリに記録し、次回監査が
   「前回からの差分」を追えるようにする
